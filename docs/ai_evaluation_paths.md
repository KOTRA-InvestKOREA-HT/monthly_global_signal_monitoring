# AI 근거 평가의 두 경로 (2026-09-04)

## 1. 왜 두 경로가 생겼나

보고서 파이프라인은 여섯 단계인데 API 키가 필요한 것은 하나뿐이다.

| 단계 | 명령 | API |
|---|---|---|
| 수집(크롤링) | `npm run collect` | 불필요 |
| 기술 관련성 필터 | `npm run filter:relevant` | 불필요 |
| 투자 시그널 분류 | `npm run filter:investment` | 불필요 |
| **AI 근거 평가** | `npm run summarize:ai` | **필요** |
| 게시 입력 검증 | `npm run validate:report-inputs` | 불필요 |
| PDF 생성 | `npm run report:pdf` | 불필요 |

이 한 단계가 막히면 보고서가 안 나온다. 2026-09-04 현재 그 상태다. 그래서 같은 자리를
사람이 채우는 경로를 만들었다.

접합부는 JSON 행에 붙는 필드 10개다. 이 값이 채워지면 검증기와 PDF는 그것이 API에서 왔는지
사람이 넣었는지 구분하지 않는다.

```text
ai_signal_supported             ai_entity_supported
ai_target_technology_supported  ai_indicator_supported
ai_leading_indicator_supported  ai_event_stage
ai_summary_quality              ai_summary_ko
ai_summary_en                   ai_summary_reason
```

## 2. 키가 막힌 경위

학교에서 받은 키는 OpenAI 키가 아니다. 32자에 `sk-` 접두사가 없다. Claude·Gemini까지 한 키로
쓰는 기관 게이트웨이 키다.

게이트웨이 주소는 `https://factchat-cloud.mindlogic.ai/v1/gateway/chatbots/3798`이고, 키 없이
엔드포인트만 조사한 결과는 다음과 같다.

| 엔드포인트 | 응답 | 해석 |
|---|---|---|
| `POST /chat/completions` | 401 (Bearer token 없음) | **존재함**. 인증만 하면 됨 |
| `POST /responses` | 404 Not Found | **미지원** |
| `GET /models` | 404 Not Found | 목록 조회 미지원 |

파이프라인은 `/v1/responses`(신형)만 쓴다. `reasoning`, `text.verbosity`, strict `json_schema` 같은
Responses API 전용 기능을 쓰기 때문이다. 그래서 **키가 아니라 요청 형식이 안 맞는 상태**다.

추가로, 이 게이트웨이는 챗봇(`chatbots/3798`) 단위로 모델이 고정돼 `model` 파라미터를 받지
않는다. 그러면 `luna → terra` 2단 재요약이 같은 모델을 두 번 부르는 것이 된다. 직전 정상 실행
기준으로 그 재요약이 전체 호출의 40%였으므로 그대로 두면 순수 낭비다.

게이트웨이 대응 코드는 한 번 작성했다가 `0724a96`에서 되돌렸다. 필요하면 `216d5af`에서 꺼낼 수
있다.

## 3. 두 경로 비교

| | API 경로 | 브리프 경로 |
|---|---|---|
| 스크립트 | `summarize_signal_evidence.mjs` | `build_report_brief.mjs` + `merge_summary_batches.mjs` |
| 입력 단위 | 행 1개 = 요청 1개 | 기사 84개를 파일 하나로 |
| 행당 본문 | 3,600자 | 기사당 900자 |
| 호출/작업량 | 243회 API 호출(174 + 재요약 69) | 붙여넣기 1회 + 응답 1회 |
| 소요 | 약 12분 자동 | 사람이 붙여넣는 시간 |
| 판정 맥락 | 행마다 독립. 앞 행이 뒤 행에 영향 없음 | 174건이 한 맥락 |
| 캐시 | 있음(프롬프트 버전 + 입력 기준) | 없음 |
| 감사 추적 | 모델명·티어·프롬프트 버전·캐시 키 기록 | `source=manual_chat_handoff`, `tier=manual`만 |
| 비용 | 토큰 과금 | 없음 |

## 4. 공유되는 것과 갈라지는 것

두 경로가 다른 결론을 내면 보고서의 의미가 사라지므로, 판정에 관여하는 코드는 한 벌만 둔다.

| 항목 | 위치 | 공유 |
|---|---|---|
| 승인 계산 | `computeSignalSupport()` | 예 |
| 요약문 문구 정리 | `summaryHeadlineDetail()`, `englishHeadlineDetail()` | 예 |
| 관련성 면제 판별 | `isRelevanceExempt()` | 예 |
| 한국어 표기 정규화 | `normalizeKoreanSummaryText()` | 예 |
| 행 식별 | `rowIdentity()` | 예 |
| **판정 기준 프롬프트 문구** | 각 스크립트에 따로 | **아니오** |

마지막 항목이 현재 유일하게 갈라져 있다. API 프롬프트는 `summarize_signal_evidence.mjs`의
`callOpenAI()` 안에, 브리프 지침은 `build_report_brief.mjs`의 `instructions()` 안에 각각 쓰여 있다.
같은 기준을 다른 문장으로 서술한 상태다.

**이것이 지금 가장 큰 미해결 항목이다.** 브리프로 테스트하며 판정 기준을 다듬어도 그 개선이 API
경로에 반영되지 않는다. 나중에 API로 전환하는 순간 판정이 달라지고, 안정화했다고 본 결과를
다시 검증해야 한다.

해결 방향은 기준 문구를 별도 모듈로 빼서 양쪽이 렌더링하게 하는 것이다.

```text
scripts/signal_judgement_rules.mjs   ← 기준 문구 한 벌
        ├─ API 프롬프트가 조립
        └─ 브리프 지침이 조립
```

## 5. 브리프 경로의 구조

원본 174행을 그대로 내보내면 65만 자가 되어 한 번에 넣을 수 없다. 세 가지로 줄인다.

| 방법 | 근거 |
|---|---|
| 기사 단위로 합치기 | 174행이 실제로는 **기사 84개**다. 같은 기사가 시그널마다 중복 계상돼 있었다 |
| 상용문구 제거 | 위험고지, 네비게이션, 반복 문단 |
| 기사당 900자 상한 | |

결과는 약 9만 자짜리 파일 하나다.

판정은 여전히 행 단위로 받는다. PDF가 (기업 × 시그널) 칸을 그리기 때문이다. 그래서 기사 본문은
한 번만 싣고 그 기사에 걸린 판정 대상을 `ref` 목록으로 붙인다.

응답은 짧은 필드명(`e`, `t`, `i`, `l`, `ok`)을 쓰고 탈락 대상은 한 문장 요약만 받아 약 5.7만 자로
줄였다. 한 응답에 안 끝나면 나눠 저장해도 `ref`로 합쳐진다.

병합은 fail-closed다. 모르는 `ref`, 중복, 누락, 잘못된 값, 빈 요약문, 브리프 생성 후 원본이 바뀐
경우 모두 **원본 파일을 건드리지 않고** 종료한다.

## 6. 결과가 달라질 수 있는 요인

같은 달을 두 경로로 돌려도 완전히 같은 결과가 나오지는 않는다.

1. **본문 분량** — 900자 대 3,600자. 긴 기사 뒤쪽에만 있는 근거는 브리프에 실리지 않는다.
   `--max-article-chars`로 올릴 수 있다.
2. **판정 독립성** — API는 행마다 별도 호출이라 3번 대상의 판정이 2번에 영향을 줄 수 없다.
   브리프는 174건을 한 맥락에서 보므로 앞뒤가 서로 기준에 영향을 준다. 브리프에 "대상마다
   독립적으로 판정하고 통과 비율을 맞추려 하지 말라"고 명시했으나 완전히 없앨 수는 없다.
3. **모델** — API는 `gpt-5.6-luna`/`terra`, 브리프는 사람이 고른 채팅 모델이다.
4. **프롬프트 문구** — 4절의 미통합 항목.

따라서 브리프로 뽑은 승인 건수를 API 경로의 예상치로 그대로 쓰면 안 된다.

## 7. 검증된 사실

2026년 8월분(투자 109 + 사업동향 65 = 174행)으로 확인했다.

- 브리프 생성: 기사 84건, 판정 대상 174건, 89,725자
- 병합 후 게시 입력 검증 통과(오류 0건), 한글 PDF 5페이지
- **같은 판정을 넣었을 때 승인 수가 API 실행과 정확히 일치**했다(투자 1건, 사업동향 23건).
  두 경로가 같은 승인 규칙을 쓴다는 뜻이다.
- 응답을 두 파일로 나눠 저장해도 174건이 정상 병합됐다.
- 실패 모드 확인: 응답 누락, 없는 `ref`, 잘린 JSON 모두 원본을 변경하지 않고 거부했다.

## 8. 아직 정하지 않은 것

1. **판정 기준 문구 통합** (4절). 브리프로 튜닝할 계획이라면 이것이 선행돼야 한다.
2. **게이트웨이 어댑터를 만들 것인가.** `/chat/completions` 경로를 붙이면 학교 키로 자동 실행이
   가능하다. 구조화 출력(`json_schema`) 지원 여부와 고정 모델의 판정 품질은 미확인이며, 키가
   있으면 호출 1~2번으로 확인된다.
3. **선행성 기준.** 현재 `committed`·`completed` 사건은 승인하지 않는다. 표지가 "투자 확정 전
   선행 징후"를 명시하므로 완화하면 보고서가 표방하는 내용이 달라진다. 8월 기준 109행 중 55행이
   이 단계였다.
4. **브리프 본문 상한.** 900자를 유지할지, API와의 격차를 줄이려고 올릴지.
5. **운영 방식.** 브리프를 테스트 전용으로 두고 API가 확보되면 전환할지, API 지원이 안 나오면
   브리프를 상시 운영으로 쓸지.

## 9. 브랜치 상태

| 브랜치 | 내용 |
|---|---|
| `main` (`0724a96`) | 시그널 판정 수정, 표지 로고, 캐시 보존까지 반영. 브리프 경로 없음 |
| `feature/manual-ai-handoff` (`d917cb5`) | 브리프 경로. main 대비 7개 파일 |
| `216d5af` (되돌림) | 게이트웨이 대응 코드. 필요하면 여기서 꺼낸다 |

브리프 경로를 상시로 쓸지 테스트 전용으로 둘지 정해지기 전에는 머지하지 않는다.

## 10. API로 전환할 때 확인할 것

1. 저장소 secret `OPENAI_API_KEY`가 실제 OpenAI 키인지, 게이트웨이 키인지
2. 게이트웨이면 `OPENAI_BASE_URL`과 `/chat/completions` 어댑터가 필요하다
3. 프롬프트 버전이 바뀌었으면 캐시가 전량 무효화되어 174행을 다시 평가한다(약 12분)
4. 전환 후 첫 실행 결과를 브리프 결과와 대조해 승인 건수 차이를 확인한다
5. 차이가 크면 6절의 네 가지 요인 중 무엇 때문인지 먼저 가린다
