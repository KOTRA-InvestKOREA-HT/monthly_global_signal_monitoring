# HTML → PDF 보고서 시험 이전 (2026-09-10)

보고서의 네 가지 페이지(표지, 시그널 매트릭스, 기업별 시그널 상세, 품목별 글로벌
사업동향)를 모두 HTML/CSS로 다시 만들고 헤드리스 Chrome으로 인쇄해 기존 reportlab
출력과 비교했다. 이번 단계의 목적은 디자인 재현이 가능한지, 그리고 그 판단을
눈대중이 아니라 숫자로 할 수 있는지 확인하는 것이다.

## 결과

네 종류 페이지의 모든 텍스트 기준선이 원본 좌표와 **최대 0.8pt** 차이다. 표의 좌측
시작점(25pt)과 폭(242pt), 상세 페이지의 흰 박스 높이(293.7pt)와 청록 박스
높이(95.7pt), 품목 카드 높이(159.6pt)는 정확히 일치한다. 한국어·영어 모두 7페이지로
기존과 같고, 어느 페이지에서도 푸터 위로 넘친 내용이 없다.

`scripts/verify_report_layout.mjs`가 이 비교를 자동으로 한다. Chrome에
렌더된 페이지의 실제 좌표를 물어 `build_pdf_report.py`의 좌표와 point 단위로
대조하고, 1pt를 넘으면 종료 코드 1을 낸다. 남은 페이지를 옮길 때 이 도구가
합격 기준이 된다.

## 무엇이 실제로 좋아지는가

매트릭스 페이지는 지금 두 개의 39행 표로 **하드코딩**돼 있다.

```python
draw_matrix_table(report, profiles[:39], ...)   # build_pdf_report.py:1354
draw_matrix_table(report, profiles[39:], ...)   # build_pdf_report.py:1355
```

타겟기업을 120개로 늘려 실제로 돌려봤다. reportlab 출력은 오른쪽 표가 범례를
덮어썼고, **85~120번 36개사가 어느 페이지에도 나오지 않았다.** 그러면서
`clipped_text_count: 0`, `pages: 7`로 성공을 보고했다. 폭 기준 잘림만 세고
세로 넘침은 세지 않기 때문이다. 현재 타겟은 77개사이고 계산상 81개사 근처에서
이 일이 시작된다.

같은 120개사를 HTML로 인쇄하면 매트릭스가 3페이지로 나뉘고, 마지막 페이지의
짧은 열도 정상으로 보이며, 범례는 제자리에 남는다. 누락은 없다.

상세 페이지에서는 `draw_detail_page`의 탐색 루프가 통째로 없어졌다. 원본은
(시그널 본문 줄 수, 사업현황 본문 줄 수) 아홉 개 조합을 작은 것부터 시도해 페이지에
들어가는 마지막 조합을 고른다. 손으로 만든 제약 해결기다. HTML에서는 각 행이 제
글만큼 높고 박스가 그걸 따라가므로 탐색할 것이 없다. 남은 것은 그 사다리의 천장과
같은 값의 `line-clamp` 두 줄뿐이다.

영문 상세 페이지의 청록 박스도 같은 방식으로 단순해졌다. 타겟품목 이름이 라벨 옆에
안 들어가면 원본은 폭을 재서 `wrapped` 분기를 타고 박스 높이를 15pt 키운다.
HTML에서는 `flex-wrap` 한 줄이 같은 일을 한다.

품목별 사업동향 페이지의 `paginate_item_cards`도 없어졌다. 원본은 카드 높이를
본문 줄 수와 여백 상수로 미리 계산해 커서를 굴리며 페이지를 나눈다. 새 경로는
카드를 한 번 렌더한 뒤 **Chrome에게 각 카드가 실제로 몇 pt인지 물어서** 나눈다.
높이를 예측하는 대신 배치한 엔진에게 묻는 것이다. 카드 8개로 시험하니 3페이지로
갈라지고 넘침이 없었다.

영문 표지에서도 차이가 드러났다. 지표 라벨이 길어지면 원본은
`short_text_to_width`로 라벨을 자르거나 설명을 지운다. HTML에서는 라벨과 설명이
flex 축소 우선순위로 자리를 협상해, 라벨은 온전히 남고 설명이 먼저 줄어든다.
결과적으로 영문 표지에서 잘리는 문구가 없어졌다.

## 곁다리로 고친 것

영문 보고서에서 같은 품목명이 품목별 페이지에서는 `Robot LiDAR`로, 상세 페이지에서는
`robot LiDAR`로 나왔다. 품목별 카드만 `item_target_text`로 첫 글자를 올리고
상세 페이지의 `target_section_for_profile`은 원문을 그대로 썼기 때문이다.
후자도 같은 함수를 쓰게 했다. 첫 글자만 올리므로 `LiDAR`, `GMP`, `RF` 같은 약어는
그대로 남고 국문은 영향이 없다. reportlab 경로에도 같이 적용된다. 영문 77개 기업 중
67개가 소문자로 시작하던 값이었다.

## 구조

```
scripts/report_view_model.py    데이터 판단 → JSON  (build_pdf_report.py를 import)
                                표지·매트릭스·상세 세 종류를 모두 담는다
scripts/report_html.mjs         JSON → HTML 문자열  (순수 함수, 파일·브라우저 접근 없음)
scripts/build_html_report.mjs   위 둘을 엮어 Chrome으로 PDF 인쇄
scripts/verify_report_layout.mjs  렌더 결과를 원본 좌표와 대조
```

데이터 판단(국가명, 산업 분류, 어느 칸이 켜지는지, 각주의 세 가지 집계)은
`build_pdf_report.py`에서 그대로 import한다. 두 벌로 갈라지면 반드시 어긋나기
때문이다. 옮긴 것은 배치뿐이다. `report_html.mjs`가 순수 함수라서, 나중에
같은 렌더러를 Next.js 라우트에서 그대로 써서 Vercel에 미리보기를 띄울 수 있다.

## 왜 Playwright가 아니라 Chrome CLI인가

`scripts/`의 어떤 스크립트도 node_modules를 필요로 하지 않고, Actions 워크플로에는
npm 설치 단계 자체가 없다. GitHub Ubuntu 러너에는 Chrome이 이미 있고 이 PC에도
Chrome·Edge가 있다. 페이지는 정적이고 폰트는 로컬 파일이라 드라이버가 줄
제어권이 필요 없다. `--print-to-pdf`가 `@page { size: 540pt 780pt }`를 그대로
지켜 정확히 540×780pt를 낸다. 더 정교한 제어가 필요해지면 Playwright로 올리면 된다.

## 파일 크기

Chrome은 넘겨준 글꼴 파일을 그대로 임베드한다. 가변 글꼴(10MB)을 쓰면 결과 PDF가
1.6MB가 되어 reportlab의 170KB보다 열 배 무겁다. `build_pdf_report.py`가 쓰는 것과
같은 네 개의 정적 글꼴로 바꾸니 326KB(국문)·300KB(영문)가 됐다. 좌표는 그대로다.

공문 첨부 기준으로는 셋 다 문제없는 크기지만, 이유 없이 무거울 이유도 없다.

## 알아둘 차이 하나

reportlab과 Chrome이 같은 글꼴의 같은 문자열을 **1~1.6% 다르게 잰다.** 한국어 9pt
한 줄을 reportlab은 444.89pt, Chrome은 451.80pt로 본다. 정적 글꼴을 써도 같고,
가변축 무게를 바꿔도 같다. 두 텍스트 엔진의 고유한 차이다.

그래서 긴 문단은 줄바꿈 위치가 한 단어씩 어긋날 수 있다. 글자가 없어지거나
겹치지는 않는다. reportlab이라면 박스 높이를 미리 계산해 둔 탓에 한 줄이 늘면
넘치지만, HTML 박스는 내용을 따라 커지므로 그냥 조금 길어질 뿐이다. 이번 자료의
모든 페이지에서 푸터 위로 넘친 내용은 없음을 확인했다.

## 남은 것

페이지는 다 옮겼다. 남은 것은 연결이다.

- Actions 워크플로에서 두 경로를 한동안 나란히 돌려 매달 결과를 비교한다.
- Vercel 즉석 생성 경로(`/api/report` → `build_pdf_report.py` → `api/report-dynamic.py`)
  정리. `report_html.mjs`가 순수 함수라 Next.js 라우트에서 그대로 쓸 수 있다.
- 확인이 끝나면 reportlab 경로 제거. 이번 브랜치는 아무 워크플로도 건드리지 않았고,
  기존 PDF 생성 경로는 대문자 수정 외에는 그대로다.
- 표지 제목 크기와, 시그널 요약의 머리글·설명이 한 줄에 들어가는지 여부는 아직
  Python이 계산해 view model에 실어 보낸다. 둘 다 폭을 재야 하는 판단이고 CSS는
  스스로 재지 못한다. 여기서는 HTML이 얻는 게 없다.

## 검증

`npm test` 140개 통과(신규 `tests/report_html.test.mjs` 18개 포함),
`python -m unittest discover -s tests` 10개 통과. 신규 테스트는 120개사 입력에서
모든 기업이 정확히 한 번씩 나타나는지, 범례·각주가 마지막 매트릭스 페이지에만
한 번 찍히는지, 쪽번호가 매트릭스 페이지 수만큼 이어지는지, 시그널이 없는 달은
그 사실이 적히는지, 머리글과 설명이 폭에 따라 한 문단이 되거나 두 문단이 되는지를 본다.
`node scripts/verify_report_layout.mjs --html <파일>`은 47개 기준점에서 worst
0.8pt로 통과한다. reportlab 경로도 국·영문 모두 `clipped_text_count: 0`, 7페이지로
그대로다. 실제 워크플로 실행과 Vercel 배포는 하지 않았다.
