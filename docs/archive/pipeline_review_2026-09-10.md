# 전체 파이프라인 후속 점검

범위: 수집·날짜 처리·검토 후보 생성·AI 판정 검증·캐시·PDF/HTML 데이터 모델·웹 데이터 읽기·결과 게시 코드. 정적 점검과 자동 테스트를 수행했다. 실시간 AI 판정, 외부 수집, 배포 환경 장애 주입은 하지 않았다.

## 수정 완료

1. **최종 수집본의 캐시 검사가 기업별 검사보다 느슨함.** 최종 summary가 있으면 24시간 경과와 출처·대상 설정 변경을 확인하지 않고 사용했다. 대상/출처 설정 해시, 수집 버전, 재개 버전, 유효 시간, 일시적 실패 여부를 검사하도록 통일했다. 미래 또는 잘못된 캐시 시간도 재사용하지 않는다. 기존 요약에는 해시가 없으므로 다음 실행에 한 번 갱신된다.
2. **자동 실행에서 검토 보류 목록 누락.** sourceCandidates가 반환한 deferred를 자동 실행 snapshot에 저장하지 않아 날짜·본문 없는 링크의 후속 확인 목록이 사라졌다. 목록을 저장하고 보고서 build에 전달한다. 기존 snapshot은 원자료로부터 목록을 재구성한다. 보류 항목이 있는 기업은 검토 완료 대신 근거 부족으로 집계한다.
3. **승인 총계와 실제 보고서 반영 건수 혼동.** 기존 총계는 호환성을 위해 유지하며 approved_count, report_signal_count, date_pending_count, out_of_period_count, companies_in_report를 별도 제공한다. 표시 단위는 기사·지표 후보이고 PDF에서 합쳐지는 기업/셀 개수와 동일하지 않다. 웹 UI 표시 변경까지 완료한 것은 아니다.

Node 테스트 166개, Python 테스트 10개 통과.

## 남은 개선 과제

- **데이터 묶음의 일관성:** app/api/signals/route.js는 여러 JSON을 움직이는 브랜치 ref로 각각 조회한다. 실행 중 ref가 갱신되면 세대가 섞일 가능성이 있다. 먼저 커밋 SHA를 확정해 같은 SHA에서 모두 읽고, PDF에도 같은 실행 식별자를 제공하는 방식이 적절하다. 실제 혼합 발생을 확인한 것은 아니다.
- **게시의 중간 실패:** review_report.mjs는 양쪽 PDF 생성이 완료된 뒤 게시하지만 JSON/PDF 복사는 여러 번 수행한다. 로컬 파일 복사 중 실패하면 일부만 갱신될 수 있다. Actions의 최종 커밋 전 실패는 저장소 공개를 막지만 로컬 작업 파일까지 원자적으로 복구하지는 않는다. 실행별 디렉터리와 검증된 manifest를 게시 단위로 쓰는 구조가 후속 과제다.
- **의미 정확도:** 원문 일치 검증만으로 기업 귀속·기술 적합성·선행성 해석을 검증할 수 없다. 기존 golden 비교 도구에 사람이 검토한 정답과 오탐/누락 평가를 결합해야 한다. 기사 수 증가를 정확도 향상으로 표현하면 안 된다.
- **날짜 근거의 소속:** 다른 기사 JSON-LD, 목록의 인접 날짜, 표시 없는 time 태그의 소속은 추가 검증이 필요하다. 정규식 기반 DOM 추출에는 한계가 있다.
- **지속적인 수집 차단:** 403·본문 없음·도메인 실패는 별도 상태로 남기는 현재 방향을 유지한다. 무리한 재시도나 승인 조건 완화로 미수집 문제를 숨기지 않는다.

이번 변경은 판정 기준을 완화하거나 과거 기사를 당월 기사로 승격하지 않는다. 사용자에게 노출되는 시그널 정확도 향상률은 아직 측정하지 않았다.
