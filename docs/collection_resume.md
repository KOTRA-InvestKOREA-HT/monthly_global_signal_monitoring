# 접속 실패와 수집 재개

- 접근 거부(403), 존재하지 않는 URL(404), 허용되지 않는 응답 형식(406)은 해당 요청을 재시도하지 않는다. 인증·접근 제한을 우회하는 기능은 추가하지 않았다.
- 봇 차단·확인 페이지(Imperva Incapsula, Akamai "Access Denied" + 참조 번호, Cloudflare "Just a moment..."·"Attention Required!")가 HTTP 200 으로 와도 받은 글로 쓰지 않고 `bot_challenge: <업체>` 오류로 남긴다(`detectBotChallenge`, 60,000자 이하 응답만 보고 업체 표식이 있을 때만 판정한다). 403 과 같이 다루어 재시도하지 않고, 기업을 재시도 대상으로 만들지 않으며, 호스트 일시 장애(아래 30초 쉼)로도 세지 않는다. 목록·피드·사이트맵에서 나면 403 처럼 `collection_coverage=incomplete` 이고, 상세 페이지에서 나면 그 기사만 본문 없는 행이다. 한 호스트에서 연달아 2번 차단되면 그 실행 동안 그 호스트 요청은 보내지 않고 같은 오류(`... (skipped: <호스트> challenged earlier in this run)`)로 끝낸다(`html_network.bot_challenges`·`challenge_skipped`). 2026-10 수집에서 airbus.com 이 이런 페이지를 200 으로 돌려줘 기사 5건이 차단 문구를 본문으로 저장했고, 사이트맵·목록은 오류 없이 0건이었다.
- 사이트맵 응답에 `<url>`·`<sitemap>` 항목이 하나도 없으면 `sitemap_empty` 오류로 남긴다(조용히 0건으로 끝내지 않는다).
- 공식 목록 페이지(official_pages)를 200 으로 받았는데 링크(`<a href>`)가 하나도 없고 피드도 알리지 않으면 `page_empty: 0 links` 오류로 남긴다. `sitemap_empty` 처럼 재시도하지 않고 기업을 재시도 대상으로 만들지 않으며, 공시·재무 문서(kind `filing`·`financial_report`) 페이지가 아니면 `collection_coverage=incomplete` 이다. 링크는 있는데 모두 거부되거나 `include` 에 걸러진 페이지는 오류가 아니다. 2026-10 까지 SCHOTT Pharma IR 페이지 세 곳(자바스크립트 껍데기)이 매달 오류 없이 0건이었다. 같은 껍데기라 2026-11 에 ABB /company/media, Proterial /e/press/(메타 새로고침), Cytiva news-center(자바스크립트 앱, 받은 행이 없었다)를 뺐다. Qualcomm 의 www.qualcomm.com/news/releases 는 링크 0개인 AEM 껍데기지만 qualcomm.com 이 공식(AEM) 호스트로 남아야 해서 `host_only: true` 로 둔다. 이 항목은 받지 않고 공식 호스트 선언(`configuredOfficialHosts`)에만 쓴다. 공식 호스트에는 목록 페이지와 함께 공식 피드(official_feeds)의 호스트도 들어간다.
- 목록 페이지가 광고한 피드(`discovered_feed`)는 한 번만 요청하고 재시도하지 않는다. 그 피드의 HTTP 상태 오류는 호스트 연속 실패(아래 30초 쉼)로 세지 않고, 앞선 연속 실패 수를 지우지도 않는다. WordPress 가 피드를 끈 응답("No feeds available!", 500)은 `feed_unavailable: no feeds available (status 500)` 로 남겨 기업을 재시도 대상으로 만들지 않는다. 설정한 피드(official_feeds)는 지금처럼 재시도하고 호스트 실패로도 센다. 2026-10 Texcell 의 /actualites/feed/ 500 이 재시도 3번으로 30초 쉼을 불러 홈페이지와 상세 기사 3건이 `domain_cooldown` 으로 끝났다.
- 공식 RSS/Atom 피드로 받은 기사의 원문 페이지를 읽지 못하면(요청 오류·차단, 추출 실패, 본문 200자 미만) 피드 항목의 요약(content:encoded·description, Atom content·summary)을 태그·엔티티를 지워 본문 자리에 쓴다. 요약도 200자(`ARTICLE_BODY_MIN_CHARS`) 미만이면 지금처럼 본문 없음이다. 이렇게 쓴 행은 `content_source=feed_summary`이고 `content_fetch_status`는 상세 페이지 요청 결과(`error` 등)를 그대로 두며, 실행 요약의 `feed_summary_body_count`로 센다. 2026-10 확인 기준 DNP 의 세 피드는 항목에 요약이 없어 이 경로로 본문이 생기지 않는다.
- 상세 페이지 HTML 에서 제목을 찾지 못했거나 본문이 200자 미만일 때만 보조 경로를 쓴다(제목을 찾은 페이지의 본문은 바꾸지 않는다. 바꾸면 기사 ID 가 바뀐다). 먼저 사이트 이름을 뗀 og:title·행 제목, og:title 이나 행 제목과 닮은 h1·`<title>` 으로 본문 범위를 다시 찾는다. 그래도 짧거나 제목을 못 찾았으면 페이지 스크립트의 본문을 Arc XP(`Fusion.globalContent`) → JSON-LD `articleBody` → Next.js RSC 순서로 찾고, 제목이 맞을 때만 쓴다(`content_fetch_status=fetched_embedded_arc|jsonld|rsc`). Arc 의 `content_restrictions` 나 JSON-LD 의 `isAccessibleForFree: false` 가 있는 유료·가입 기사는 꺼내지 않는다. 받은 주소가 그 기업의 공식 호스트이면서 AEM 으로 확인된 호스트(`AEM_MODEL_HOSTS`, 지금은 qualcomm.com)이고 본문이 짧으면 같은 경로의 AEM 모델(`.model.json`)을 한 번 더 본다(`fetched_aem_model`). 2026-10 까지는 공식 호스트 전체에 모델을 붙여 AEM 이 아닌 기업에서 404·403 오류만 쌓였다. 실행 요약의 `google_news_decoded_count` 는 이 상태들도 받은 것으로 센다.
- HTML/RSS 요청에서 같은 호스트의 연결 오류·시간초과·429·서버 오류가 3회 연속되면 30초간 추가 요청을 건너뛴다. 이후 요청이 있으면 하나만 시험하고 성공 시 정상화한다. 이 상태는 실행 간 저장하지 않는다. 다른 호스트는 계속 수집한다.
- Google News 링크 풀기(기사 페이지·해독 요청)는 기업이 달라도 한 차례(`createPublisherProbe`)를 지나며, 요청 사이에 1초를 둔다. 429 를 받으면 60초부터 두 배씩(Retry-After 가 더 길면 그 값) 쉬고 그 기사를 한 번 더 보낸다. 429 를 받은 기사는 중계 주소를 따라가 보지 않는다. 풀리지 않은 중계 주소·타임아웃·5xx 는 3회 연속일 때 쉰다. 한 실행에서 쉬는 시간은 180초까지이고, 그 뒤 막힌 동안 온 기사는 요청 없이 `google_probe_paused` 로 남는다. 막힘이 끝날 시각이 지나면 다음 기사로 다시 시험해 이어 간다. 요청·429·쉼·재시도·건너뜀 수는 수집 요약 `google_probe_stats` 에 남는다.
- 기업 하나가 끝날 때마다 출력 폴더의 `company_progress`에 원자료·오류를 저장한다. 다음 실행에서 그 기업의 출처 설정·사업동향 탐색 입력(자기 기술 항목·키워드 그룹·검색어)과 수집 설정·기간·수집 버전이 같고 24시간 이내면 완료된 기업을 재사용한다. 기간 마감(to_date 다음 날 0시, UTC) 뒤 3일이 지나 받은 수집본은 72시간까지 재사용한다. 그 사이 늦게 색인된 기사는 들어오지 않는다. 일시적 오류가 있는 기업은 다시 수집한다.
- 일시 오류가 상세 페이지 단계(공식 상세·모델 보강)에만 있는 기업은 처음부터 받지 않는다(`onlyDetailStepsRetryable`). 진행 파일에 출처·검색·상세 페이지별 결과를 함께 저장해 두고, 다음 실행에서 그 결과를 쓰고 멈춘 기사만 다시 요청한다. 대체 수집 여부·기업 상한·상세 페이지 상한·사업동향 후보 선택은 다시 계산하므로 결과는 같은 응답을 받은 전체 재수집과 같다. 이어 받은 진행 파일의 유효 시간은 처음 받은 시각부터 센다. 대체 수집 검색은 처음 받은 결과를 쓴다.
- 판정 실행(`review_report.mjs`)은 수집이 재시도 대상 기업을 남기면 60초 쉬고 수집기를 한 번만 더 돌린다(`collectWithRetryPass`). 끝난 기업은 위 진행 파일에서 읽고 재시도 대상 기업만 요청한다. 모델 호출은 없다. 재시도 대상 기업은 원래 "다음 실행"에서 다시 받았는데, 판정이 한 번에 끝나면 다음 실행 없이 발행까지 갔다. Issue 5(2026-10, 11월 2일 수집)가 그렇게 Dupont·Chemours·3M·Ouster·HyproMag·Texcell·DNP·Shanghai Electric Wind Power 8개 기업을 남긴 채 발행됐다. 그래도 남은 기업은 판정 상태(`status.json`)의 `collection_retryable`과 실행 요약 "Collection incomplete"에 남는다. 한 번 더 받기의 요약은 그 실행의 것이라 `request_count` 등은 두 번째 수집만 센다(`cached_company_count`가 끝난 기업 수다).
- 발행(`publish_report.mjs`)은 판정이 쓴 수집 요약에 재시도 대상 기업이 남았으면 문안을 쓰기 전에 종료 코드 65로 멈춘다. 워크플로는 `Held - retryable companies remain` 단계로 실행을 끝내고 대시보드는 "발행 보류"로 보인다. 같은 기간으로 판정을 다시 돌리면(대시보드 "크롤링 수행") 그 기업을 다시 받는다. 매달 같은 오류를 주는 사이트처럼 다시 받아도 남으면 `allow_retryable_companies`(대시보드 "발행만 실행"의 체크 상자)로 넘긴다. 발행 보류 뒤에도 "발행만 실행"은 열려 있어 멈춤이 발행을 영영 막지 않는다. 2026-11 확인으로 DNP 의 설정 주소 `https://www.dnp.co.jp/en/ir/` 는 늘 HTTP 500(dnp.co.jp/en/* 전체가 Fastly "unknown domain")이라 설정을 고칠 때까지 DNP 는 매 실행 재시도 대상이고, 그동안은 매달 넘겨야 한다. 넘긴 발행은 `latest_ai_summary_summary.json`의 `published_with_retryable_companies`에 그 기업을 남긴다. 접근 거부 같은 영구 오류는 재시도 대상이 아니라서 멈추지 않는다.
- 접근 거부 등 재시도로 해결하지 않는 오류는 결과와 함께 보존하고, 캐시 재사용 중에도 `collection_coverage=incomplete`로 유지한다. 보고서에서 기사 없음이나 검토 완료로 바꾸지 않는다.
- 전체 재수집은 CLI `--refresh true` 또는 trial 워크플로의 `refresh=true`로 한다. 보고서 워크플로의 기존 refresh도 수집 폴더를 지워 같은 효과를 낸다.
- trial과 보고서 워크플로는 기업별 진행 파일을 캐시에 저장한다. 한 기업의 수집 도중 중단되면 그 기업은 다음에 처음부터 시도하지만, 그 전에 완료된 기업은 재사용할 수 있다.

`cached_company_count`, `resumed_company_count`(멈춘 기사만 다시 받은 기업), `retryable_company_count`, `collection_coverage`로 재사용과 미완료를 확인한다. `html_network`는 실제 HTML/RSS 시도·도메인 중단 횟수·시도 시간의 합계다. PDF·보조 뉴스 직접 다운로드는 이 지표에 포함하지 않는다. 병렬 요청 시간의 합계는 전체 실행 시간이 아니다. `request_count`와 재시도·제외 표본 등 실행 집계는 이번 실행에서 발생한 작업을 나타내며, 캐시된 과거 요청과 이어 받으며 다시 쓴 단계의 요청·제외는 다시 더하지 않는다.

원문을 읽지 못한 기업의 신호가 누락될 가능성은 남는다. 이를 숨기거나 다른 날짜의 과거 결과를 이번 달 결과로 대체하지 않는다.
