# 지표 근접 규칙 (판정 전 결정적 전처리)

## 1. 왜 넣었나

2026-09 회차에서 투자 시그널 109건 중 **107건이 거절**됐다. 거절 사유는 중복 집계로 이렇다.

| 사유 | 건수 |
|---|---|
| 선행성 없음 | 87 |
| 지표 근거 없음 | 81 |
| 타겟 기술 근거 없음 | 79 |
| 주체 불일치 | 12 |

분류기가 통과시킨 것을 AI가 다시 버리고 있었다. 원인은 분류기가 **기사 전체에서 단어를 세기**
때문이다. 네비게이션이나 실적발표 상용문구에 있는 "supply chain" 하나로도 점수가 4점을 넘는다.

점수는 이 문제를 못 잡는다. 실제로 걸러졌어야 할 행의 점수가 오히려 높다.

```text
점수 9  HyproMag        "Welcome to Mkango Resources Ltd."       ← 회사 홈페이지
점수 8  Applied Materials  "…Announces Third Quarter 2026 Results"  ← 실적발표 위험고지
점수 8  3M              "…Reports Second-Quarter 2026 Results"
```

승인된 2건의 점수는 5와 6이었다. **점수로는 후보를 못 좁힌다.**

## 2. 규칙

> 매치된 지표 용어가 **회사를 가리키는 문장 안에** 있어야 한다.

AI 없이 계산된다. `scripts/classify_investment_signals.mjs`의 `indicatorProximity()`다.

- 문장 단위로 쪼갠 뒤, 회사 언급과 지표 용어가 **같은 문장**에 있는지 본다
- 제목도 본문과 같이 본다
- 회사 언급은 넓게 잡는다: 전체 사명 또는 3자 이상 토큰 하나. 좁게 잡아 놓치면 진짜 시그널이
  사라지지만, 넓게 잡아 남는 것은 어차피 뒤에서 판정을 받는다. **틀릴 때 남는 쪽으로 틀린다**
- 용어 매칭은 분류기가 이미 쓰는 `includesKeyword()`를 그대로 쓴다(약어·공백 정규화 동일)

## 3. 측정

2026-09 회차 실측이다.

| | 적용 전 | 적용 후 |
|---|---|---|
| 투자 시그널 | 109행 | **55행** (−50%) |
| 사업동향 | 65행 | 65행 (미적용) |
| 본문 총량 | 1,876,745자 | **1,045,587자** (−44%) |
| **승인 결과** | 37건 | **37건** |

걸러졌을 54건 중 AI가 승인한 것은 **0건**이다.

입력 토큰이 절반 가까이 줄므로 API 비용, 브리프 붙여넣기 분량, 모델 생성 시간이 함께 준다.

## 4. 사업동향에는 걸지 않는다

같은 규칙을 사업동향 65행에 걸어보면 **승인 35건 중 17건을 잘못 버린다**(Heidenhain,
Siemens-Gamesa, Evonik, West Pharmaceutical, Boeing, Umicore, Norsk Hydro 등).

당연한 결과다. 사업동향은 "이 회사가 무엇을 하고 있는가"를 보는 것이라 지표 용어와의 동시출현을
요구하지 않는다. 투자 시그널 전용이다.

## 5. 지금은 shadow다

기본값은 `--indicator-proximity shadow`다. 세 가지 값을 받는다.

| 값 | 동작 |
|---|---|
| `shadow` (기본) | 판정만 기록하고 행은 그대로 둔다 |
| `enforce` | `indicator_near_company !== true`인 행을 제외한다 |
| `off` | 계산하지 않는다 |

**한 회차 결과로 켜면 안 된다.** 이번 회차의 투자 승인이 2건뿐이라 "승인행을 안 버린다"는
근거가 얇다. 2건 다 살아남은 것은 사실이지만, 2건으로 규칙을 확정할 수는 없다.

그래서 `prepare-report-brief.yml`이 회차마다 `scripts/report_proximity_shadow.mjs`를 돌려
**걸러졌을 행을 Actions 요약에 표로 남긴다.** 확인할 것은 하나다.

> 걸러졌을 목록에 있는 행이 그 회차의 AI 판정에서 승인됐는가?

승인된 것이 나오면 규칙이 너무 강한 것이므로 켜지 않는다. 몇 회차 동안 0건이면 `enforce`로
바꾼다. 판정 기록은 요약 파일의 `indicator_proximity`에, 행별로는
`indicator_near_company` / `indicator_near_company_sentence` 필드에 남는다.

## 6. 회차마다 할 일 (섀도 판독)

수집 워크플로가 끝나면 Actions 실행 요약에 이런 표가 붙는다.

```text
### 지표 근접 규칙

기록만 함(shadow). 109건 중 **54건(50%)**이 걸러졌을 것이고, 55건이 남습니다.

걸러졌을 행 54건 중 상위 25건입니다.
이번 회차의 AI 판정에서 이 중 승인된 것이 있으면 규칙이 너무 강한 것이므로 켜면 안 됩니다.

| 기업 | 지표 | 점수 | 기사 |
| --- | --- | ---: | --- |
| HyproMag | 공급망·지정학 리스크 대응 | 9 | Welcome to Mkango Resources Ltd. |
```

**볼 것은 하나다.** 이 목록에 있는 행이 그 회차 AI 판정에서 승인됐는가.

```bash
node -e '
const rows = require("./outputs/latest_investment_signals.json");
// 이 회차가 새 분류기로 돌았는지 먼저 본다. 주석이 없는 파일에서는 모든 행이 "걸러졌을 행"으로
// 세어져, 규칙이 승인행을 버리는 것처럼 잘못 보인다.
if (!rows.some((row) => "indicator_near_company" in row)) {
  console.log("이 파일에는 근접 판정이 없습니다. 새 분류기로 수집을 다시 돌린 뒤 확인하세요.");
  process.exit(1);
}
const dropped = rows.filter((row) => row.indicator_near_company !== true && row.ai_signal_supported === true);
console.log("걸러졌을 행 중 승인된 것:", dropped.length);
dropped.forEach((row) => console.log(" -", row.company, "|", row.title));
'
```

- **0건이면** 그 회차는 규칙이 안전했다는 뜻이다. 기록해 두고 다음 회차로 넘어간다.
- **1건이라도 나오면** 켜지 않는다. 그 행을 이 문서에 남기고, 왜 회사 언급을 못 찾았는지
  (사명 표기 차이, 대명사 지시, 문장 분리 실패) 확인해 규칙을 고친다.

세 회차 연속 0건이면 워크플로의 `--indicator-proximity shadow`를 `enforce`로 바꾼다. 그때부터
걸러진 행은 `latest_investment_signals.json`에 아예 실리지 않으므로, 위 확인은 더 이상 안 된다.
되돌리려면 값을 `shadow`로 되돌리기만 하면 된다 — 다른 코드는 손대지 않는다.

### 판독 기록

| 회차 | 걸러졌을 행 | 그중 승인 | 판단 |
|---|---|---|---|
| 2026-09 | 54 / 109 | **0** | 유지(shadow) |

2026-09 회차는 규칙을 만들기 전에 수집이 끝나 있었으므로, 저장된 파일에 근접 판정이 없다.
위 수치는 그 회차의 행에 `indicatorProximity()`를 나중에 걸어 다시 계산한 값이다. 다음 회차부터는
분류기가 직접 기록하므로 위 명령이 그대로 동작한다.

## 7. 남은 것

**선행성(87건)과 타겟 기술 근거(79건)는 아직 AI가 판정한다.** 이 규칙은 지표 근거(81건)만
건드린다. 선행성은 시제·양태 판단이라 키워드로 재현하기 어렵고, 타겟 기술 근거는
관련성 필터가 이미 보고 있으나 임계값이 낮다(threshold 1). 둘 다 별도 과제다.
