# API 키 없이 보고서 만들기 (브리프 반입)

## 1. 흐름

```bash
npm run collect && npm run filter:relevant && npm run filter:investment   # API 불필요
npm run brief                    # 파일 하나 생성

#  outputs/manual_summary/report_brief.md 를 채팅에 붙여넣거나 첨부
#  받은 JSON 배열을 outputs/manual_summary/responses/reply.json 으로 저장

npm run merge:brief              # 되돌려 넣기
npm run validate:report-inputs && npm run report:pdf
```

붙여넣기 **한 번**, 응답 **한 번**이다. 브리프 안에 판정 규칙과 출력 형식이 모두 들어 있으므로
파일만 주면 된다.

## 2. 왜 한 파일에 들어가는가

파이프라인에서 API가 필요한 단계는 근거 평가 하나뿐이다. 나머지는 전부 로컬 계산이다.
문제는 부피였는데, 원본 174행을 그대로 내보내면 65만 자가 된다. 세 가지로 줄인다.

| 줄이는 방법 | 효과 |
|---|---|
| 기사 단위로 합치기 | 174행 → **84개 기사**. 같은 기사가 여러 시그널로 중복돼 있었다 |
| 상용문구 제거 | 위험고지, 네비게이션, 반복 문단 |
| 기사당 본문 상한 | 기본 900자 |

결과는 **89,725자짜리 파일 하나**다. 채팅 한 번에 들어간다.

판정은 여전히 행 단위로 받는다. PDF가 (기업 × 시그널) 칸을 그리기 때문이다. 그래서 기사 본문은
한 번만 싣고, 그 기사에 걸린 판정 대상을 `ref` 목록으로 붙인다.

```text
### 12. Nexeon Achieves ISO 9001 Certification for Gunsan Plant
출처: Nexeon - News · 게시일: 2026-08-28

판정 대상:
- `INV-014` Nexeon | 유치필요 기술: 실리콘 음극재 | S2 생산 확대 및 다변화 의지
- `REL-031` Nexeon | 유치필요 기술: 실리콘 음극재 | 글로벌 사업현황

(본문 900자)
```

## 3. 응답 분량

응답은 판정 174건이다. 짧은 필드명(`e`, `t`, `i`, `l`, `ok`)을 쓰고, **승인되지 않은 대상은 한 문장
요약만** 요청한다. 보고서용 한·영 요약문은 `ok=1`인 대상에만 쓴다.

| | 크기 |
|---|---|
| 필드명을 다 쓰고 전 행에 요약문 | 21만 자 |
| **현재 방식** | **약 5.7만 자** (승인 24건 기준) |

그래도 한 응답에 안 담길 수 있다. 브리프에 "끊기면 이어서 출력하라"고 적혀 있고, 병합기는
`responses/` 안의 `.json`을 전부 읽어 `ref`로 합치므로 **응답을 여러 파일로 나눠 저장해도 된다.**

## 4. 판정 기준은 API 경로와 같다

승인값은 답변의 `ok`를 그대로 믿지 않고 `computeSignalSupport()`로 다시 계산한다. 이 함수는 API
경로가 쓰는 것과 같은 함수이며 `summarize_signal_evidence.mjs`에 한 벌만 있다. 규칙을 두 벌로
두면 어느 경로로 만든 보고서냐에 따라 승인 기준이 달라진다.

관련성 면제 기업은 브리프에서 판정 대상 줄에 `**면제**`로 표시되고, 그 대상은 타겟 기술 근거를
승인 조건으로 요구하지 않는다.

투자 시그널 요약문은 API 경로와 같은 문구 정리를 거치므로 PDF에서 같은 문체로 보인다.

## 5. 병합은 fail-closed다

다음 중 하나라도 발견되면 **원본 파일을 건드리지 않고** 종료 코드 1을 반환한다.

- JSON 배열을 찾지 못함
- manifest에 없는 `ref`, 같은 `ref` 중복, 응답이 없는 대상
- 판정 값이 boolean도 0/1도 아님
- 정의에 없는 `stage` 또는 `q`
- 요약문 또는 판정 사유가 빔
- 브리프를 만든 뒤 원본 행이 바뀜(수집을 다시 돌린 경우)

마지막 항목 때문에, 브리프를 만든 뒤 수집을 다시 돌렸다면 브리프도 다시 만들어야 한다.
적용 전에 확인만 하려면 `--dry-run true`를 쓴다.

## 6. 검증 결과

2026년 8월분으로 왕복 시험했다.

```text
브리프 생성      84개 기사 · 판정 대상 174건 · 89,725자
병합             174건 반영
게시 입력 검증   passed, 오류 0건
PDF              5페이지
```

기존 판정을 그대로 넣었을 때 승인 수가 API 실행 결과와 정확히 일치했다(투자 1건, 사업동향 23건).
응답을 두 파일로 나눠 저장한 경우도 174건이 정상 병합됐다.

실패 모드도 확인했다. 응답 누락, 없는 `ref`, 잘린 JSON 모두 원본을 변경하지 않고 거부했다.

## 7. 한계

**배치가 하나여도 판정은 한 맥락에서 이뤄진다.** API 경로는 행마다 독립 호출이라 3번 대상의
판정이 2번에 영향을 줄 수 없지만, 브리프는 174건을 한 번에 보고 판단하므로 앞뒤 대상이 서로
기준에 영향을 준다. 브리프에 "대상마다 독립적으로 판정하고 통과 비율을 맞추려 하지 말라"고
명시했지만 완전히 없앨 수는 없다.

**감사 추적이 약해진다.** 모델명, 프롬프트 버전, 캐시 키가 남지 않는다. 병합된 행은
`ai_summary_source=manual_chat_handoff`, `ai_summary_tier=manual`로 표시되므로 경로 구분만 된다.

**캐시가 없다.** 다음 달에 같은 기사가 다시 걸려도 처음부터 다시 판정한다.

**본문이 900자로 잘린다.** API 경로는 행당 3,600자를 쓴다. 긴 기사에서 뒤쪽에만 있는 근거는
브리프에 실리지 않을 수 있다. `--max-article-chars`로 올릴 수 있으나 파일이 커진다.
