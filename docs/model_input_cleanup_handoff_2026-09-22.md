# Claude 인계: 지표 ID 참조와 모델 입력 영어화

## 사용자 확인 사항

**타겟 기술의 한국어 원본과 한국어 보고서·화면 표기는 그대로 유지한다. 모델에게 보내는 입력에만 별도로 관리하는 영어 표현을 사용한다.** 한국어 원본을 영어로 덮어쓰거나, 보고서에서 타겟 기술을 영어로 바꾸라는 요청이 아니다.

이번 사용자 요청은 이 구분을 명시한 인계 문서 작성이다. 이 문서 작성 과정에서 아래 구현을 적용하거나 모델 API를 호출하지 않았다. 기존 작업 트리의 다른 변경은 그대로 두었다.

## 목표

한 번의 API 요청 안에서 공통 판정 기준을 한 번만 정의하고, 후보는 ID로 그 기준을 참조한다. 회사별 타겟 기술·범위 등 실제 판단에 필요한 정보는 영어로 전달한다. 별도 번역 API나 추가 교정 호출을 붙이지 않는다.

여기서 사용자 메시지는 사람이 채팅창에 입력한 말이 아니라 `review_providers.mjs`가 만드는 기사·후보 JSON을 뜻한다. 기준표와 후보 JSON은 같은 요청에 포함되므로 ID 참조 때문에 별도 파일 읽기나 API 호출이 발생하지 않는다.

## 현재 경로

- `config/investment_signal_indicators.json`: `label_ko`, `label_en`, `description_ko` 및 수집·분류용 키워드를 보관한다.
- `scripts/local_report.mjs`: 원자료에서 후보를 구성하고 `target_technology`, `target_technology_scope`, 지표명·설명 등을 붙인다. 원본 행은 `row`에 보존한다.
- `scripts/review_providers.mjs`의 `articleText`: 현재 `row`만 제외하고 기사 및 후보 필드를 직렬화한다. 같은 직렬화 경로를 Gemini와 NVIDIA가 사용하며 검증 요청은 후보 목록만 제한한다.
- `docs/local_report_review.md`: 모델에 전달되는 영어 판정 기준. 지표별 정의·포함·제외 사례가 있다.
- `scripts/review_prompts.mjs`: 공통 지시, 변형, 응답 스키마와 프롬프트 계약을 관리한다.

구현 전 타겟 기술의 실제 원본 파일, 매핑 키, 포함·제외 범위의 구조를 다시 확인한다. 앞선 조사에서 나온 29개 기술·6개 후보·날짜 문구 수는 당시 자료의 관찰값이며 상수로 가정하지 않는다.

## 1. 지표의 뜻은 공통 기준에서만 정의

모델 입력에서 투자 후보의 `indicator`, `description` 같은 반복 설명을 빼고 `id`로 해당 기준을 선택하게 한다.

| 후보 ID | 적용할 기준 |
| --- | --- |
| `investment:1` | S1 supply-chain and geopolitical risk response |
| `investment:2` | S2 production expansion and diversification intent |
| `investment:3` | S3 investment funding |
| `investment:4` | S4 technology ecosystem engagement |
| `investment:5` | S5 key strategic personnel movement |
| `relevant` | Business activity criteria |

`kind`, 기술 면제 여부, 회사별 기술 범위 등 판단에 필요한 필드는 유지한다. ID만 남기고 후보의 모든 정보를 지우라는 뜻은 아니다.

판정 기준 3번의 "matching the candidate's indicator and description"도 실제 계약에 맞게 수정해야 한다. 제거한 필드를 참조하게 두지 말고, 후보 ID에 해당하는 아래 정의를 적용하라고 명시한다. 지표 설명을 제거하기 전에 영어 공통 기준과 원래 설명을 대조하고, 의미 차이가 있으면 누락인지 의도된 범위인지 확인한다. 공통 기준의 승인 범위를 번역 작업 중 임의로 넓히지 않는다.

**`description_en`을 추가해서 후보마다 다시 보내는 것은 이 설계의 목적이 아니다.** 그렇게 하면 언어 혼용은 줄지만 중복 정의는 그대로 남는다. 한국어·영어 지표 라벨과 한국어 설명은 기존 표시·수집·분류 용도로 유지하고, 모델 입력에서만 중복 설명을 제외한다.

## 2. 타겟 기술은 한국어 원본과 영어 입력 표현을 분리

S1~S5는 모든 회사에 같은 기준이지만 타겟 기술은 회사별로 다르다. 예를 들어 일반적인 공장 증설인지, 해당 회사에서 추적하는 희토류 재활용 시설 증설인지는 기술 정보를 알아야 구분할 수 있다. 따라서 타겟 기술은 삭제하지 않는다.

권장 구조:

- 원본 `target_technology`와 한국어 보고서 표기는 유지한다.
- 영어 표현을 별도 필드나 매핑 파일에 관리한다. 기존 안정적인 기술 ID가 있다면 그 ID를 사용한다. 배열 순서나 임의의 번호로 연결하지 않는다.
- 모델 입력을 구성할 때 영어 표현을 선택한다. 원본 객체나 저장된 `row`를 수정하지 않는 변환 계층을 둔다.
- `target_technology_scope.includes/excludes` 등 세부 범위도 확인한다. 한국어가 남아 있다면 영어 대응 표현을 준비하되, 포함·제외 조건과 기술 면제 플래그를 보존한다.
- 재료명·공정·용도·순도·재활용 대상 등 구분에 필요한 조건을 빠뜨리지 않는다. 약어와 고유명사는 원문 의미에 맞게 유지한다.

구조를 설명하는 가상 예시이며 실제 구현 필드명은 저장소 구조에 맞춰 정한다.

원본 및 표시 데이터:

```json
{
  "target_technology": "사용후 영구자석 고순도 희토류 추출 및 재활용",
  "target_technology_en": "Extraction and recycling of high-purity rare earths from end-of-life permanent magnets"
}
```

모델용 후보 표현:

```json
{
  "id": "investment:1",
  "kind": "investment",
  "target_technology": "Extraction and recycling of high-purity rare earths from end-of-life permanent magnets",
  "relevance_exempt": false
}
```

위처럼 모델용 `target_technology` 키에 영어를 넣어도 원본 필드를 덮어쓰는 것은 아니다. **별도 객체를 만들어 전송할 때만 표현을 바꾸는 것**이다. 같은 정보의 한영 표현을 모델 입력에 둘 다 넣지 않는다.

번역 누락은 사전 검증에서 기술 ID와 함께 드러나게 한다. 모르는 기술을 빈 문자열로 보내거나, 요청마다 자동 번역하거나, 한국어로 조용히 대체하지 않는다. 기술 면제여서 원래 기술 정보가 없는 경우와 번역 누락은 구별한다.

## 3. 날짜의 표시용 문구 정리

`date_label`, `date_note`가 표시용인지 실제 판단에도 쓰이는지 확인한다. 다른 구조화 필드가 동일한 정보를 담으면 모델 입력에서 제외할 수 있다. 고유한 충돌 근거가 들어 있으면 버리지 말고 영어 또는 구조화된 표현으로 보존한다.

`published_at`, `published_month`, `date_status`, `date_placement`, 보고 기간 및 실제 날짜 근거 등 판단에 필요한 값은 유지한다. 보고서의 한국어 날짜 표시를 바꾸지 않는다.

## 4. 기사 원문과 표시 데이터는 별도

모델 입력을 영어로 정리한다는 것은 프로그램이 붙이는 설명·메타데이터에 대한 것이다. 기사 제목·본문·`evidence`에 있는 한국어, 일본어, 독일어 등을 일괄 삭제하거나 영어로 번역하지 않는다. 원문 인용 검증에 필요한 증거를 보존한다.

화면·한국어 PDF·수집 키워드·기술 원본 설정도 모델 입력과 별개다. 모델용 JSON을 만들기 위해 이 자료들을 영어로 치환하지 않는다.

## 5. API·로컬·캐시 계약

- 1차 요청, 수리 요청, 2차 검증 및 프롬프트 변형이 동일한 모델용 표현을 사용하도록 한다. 검증 대상 후보를 제한하는 현재 동작은 유지한다.
- 로컬 검토자에게 제공하는 기사 자료도 가능한 한 같은 표현을 쓰게 하되, 로컬 상태·보고서 생성에 필요한 원본은 보존한다. 표시용 원자료와 판정용 입력의 경계를 명확히 한다.
- 전송 함수에서만 번역을 바꾸면 기사 ID가 그대로일 수 있다. 실제 전달되는 기술 번역·범위·입력 계약 버전의 변경이 판정 캐시 식별자에 반영되는지 확인한다. 한국어 원본이 같다는 이유로 다른 영어 입력의 판정을 재사용하지 않는다.
- 번역 변경으로 전체 캐시가 무효화되는지 해당 기술 기사만 바뀌는지 명시한다. 현재 중단된 실행과 새 입력 실험을 구분한다. 기존 376건이나 운영 캐시를 삭제하지 않는다.

## 검증 기준

1. Gemini·NVIDIA 및 각 변형의 실제 요청 JSON에 중복 `indicator`·`description`이 없고, 후보 ID에 대응하는 공통 기준이 존재한다.
2. 코드가 더 이상 제거한 필드를 판정 지시에서 참조하지 않는다.
3. 타겟 기술 번역이 실제 대상 전체를 포괄하고, 빠진 번역은 사전 검증으로 확인된다.
4. 모델용 영어 기술 표현과 포함·제외 범위가 대응하는 한국어 원본의 의미를 유지한다.
5. 모델 입력 변환 후 원본 객체, 한국어 기술명, 한국어 보고서 표시, 수집·분류용 설정이 바뀌지 않는다.
6. 날짜 상태·충돌 근거·기사 원문과 인용 가능성이 보존된다.
7. 영어 번역이나 모델용 입력 계약이 달라지면 적절한 캐시 식별자가 달라진다.
8. 모델 입력을 구성하는 과정에 추가 API 호출이 없다. 실제 모델 실험은 별도 소수 기사와 명시적인 요청 예산으로 수행한다.

## 해석상의 한계

입력 끝의 한국어가 영향을 줄 가능성은 있으나, 시스템 지시보다 반드시 강하거나 콩글리쉬의 직접 원인이라고 입증된 것은 아니다. 이 작업의 확실한 목적은 중복 정의와 언어 혼용을 줄이고 기준의 관리 위치를 명확히 하는 것이다. 문안 품질과 토큰 절감량은 별도로 측정해야 한다.

후보 간 한국어 요약의 영향도 완전히 사라지지 않는다. 앞선 관찰의 8/376건은 전체 기사 기준이며 요약이 있는 32개 기사 기준으로는 8/32건이다. 어느 비율만으로 영향을 단정하지 않는다. 이번 작업에서는 출력 순서나 후보별 호출을 추가 변경하지 않는다.
