# 구조 정리 (2026-09-21)

외부 검토가 제기한 항목을 저장소에서 직접 확인하고, 결과가 어긋날 수 있는 것부터 고쳤다. 보고서 내용과 승인 규칙은 바꾸지 않았다.

## 확인한 사실

| 항목 | 검토 주장 | 확인 결과 |
|---|---|---|
| CSV/JSON 불일치 | 투자 시그널 JSON 28건, CSV 109건 | 사실. CSV 109/65/431행은 모두 `collected_at` 2026-09-04, JSON은 2026-09-20 |
| 전월 계산 분기 | 웹 API는 UTC, 자동 실행은 KST, 화면은 브라우저 시간 | 사실. 세 구현을 모두 확인하고 경계에서 재현 |
| 승인 조건 이중 구현 | JS와 Python에 각각 존재 | 사실. 지표 3·5 변경 때 네 지점을 함께 고쳐야 했음 |
| GitHub 환경변수 처리 차이 | 실행 버튼만 공백·따옴표 제거 | 사실. 세 라우트가 각각 다른 방식 |
| 추적된 생성물 | `.pyc`, 일회성 테스트 로그 | 사실. `scripts/__pycache__/`는 `.gitignore`에 있으나 파일은 이미 추적 중이었음 |
| Python 수집기 "동등한 구현" | README 설명이 틀림 | 사실. 아래 참조 |

## 1. 낡은 CSV와 추적된 생성물

`outputs/latest_*.csv`는 구형 키워드 스크립트(`collect`, `filter:relevant`, `filter:investment`)만 만든다. 월간 보고서 경로인 `scripts/review_report.mjs`는 JSON만 쓰고, 워크플로의 `file_pattern`도 `outputs/latest_*.json`뿐이다. 그래서 커밋된 CSV는 마지막 수동 실행 시점에 멈춰 있었고, `ai_*` 승인 컬럼을 단 채 16일 지난 판정을 보여 주고 있었다. 읽는 코드는 없다.

추적에서 내리고 `.gitignore`에 넣었다. 파일 자체는 작업 디렉터리에 남는다.

- `outputs/latest_investment_signals.csv`, `outputs/latest_relevant_signals.csv`, `outputs/latest_company_signals.csv`
- `outputs/followup_tests.txt` (일회성 테스트 로그)
- `scripts/__pycache__/build_company_technology_map.cpython-312.pyc`

## 2. 전월 계산 통일 — `scripts/report_month.mjs`

전월이 언제인지를 세 곳이 각자 계산했다.

| 위치 | 기준 시간대 |
|---|---|
| `scripts/report_period.mjs` (CLI·Actions) | 한국 시간 |
| `app/api/trigger-crawl/route.js` (실행 버튼) | UTC |
| `app/page.jsx` (화면) | 브라우저 현지 시간 |

한국 시간 9월 1일 0시 30분(= UTC 8월 31일 15시 30분)에 자동 실행은 8월을 고르지만 실행 버튼은 7월 수집을 보낸다. 버튼을 누른 사람은 8월 보고서를 기다린다. 화면은 브라우저 시간이라 해외에서 열면 또 다른 달을 보여 준다.

`scripts/report_month.mjs` 하나로 모았다. 보고서의 기준 시간대인 한국 시간을 쓰고, 브라우저 번들에도 들어가므로 `node:` 모듈을 가져오지 않는다. `next build`로 클라이언트 번들에 정상적으로 들어가는 것을 확인했다.

테스트(`tests/report_entrypoints.test.mjs`)는 경계·연말·윤년을 검사하고, 세 파일이 공용 모듈을 쓰는지와 자기 달력 계산을 다시 들이지 않았는지도 본다.

## 3. 승인 규칙 — 공용 상수와 양쪽 판정 비교

승인 규칙은 `scripts/validate_report_inputs.mjs`(판정·검증)와 `scripts/build_pdf_report.py`(발행)에 각각 구현돼 있다. 한쪽만 고치면 검증을 통과한 행을 발행 단계가 말없이 떨어뜨린다.

- 상수를 `config/approval_policy.json` 하나로 모았다(승인 가능 단계, precursor 허용 지표, 기업 단위 지표, 사업동향 고정 단계, 품목 무관 부인 문구).
- `tests/approval_parity.test.mjs`가 1,764가지 입력(지표 6종 × 단계 7종 × 품목 연결 × 면제 3종 × 결함 6종)에 대해 두 구현의 판정이 같은지 맞춘다. Python 쪽만 어긋나게 한 변이 검사로 실제로 불일치 9건을 잡아내는 것을 확인했다.
- 상수가 코드로 되돌아오면 공유가 깨지므로, 옛 값이 소스에 다시 나타나지 않는지도 검사한다.
- `reportlab`이 없는 환경에서는 발행 쪽을 부를 수 없어 건너뛴 것으로 표시한다. 조용히 통과시키지 않는다.

### 이 과정에서 찾은 불일치

사업동향 행의 `event_stage`를 Python은 `not_applicable`로 강제하는데 JS 검증은 단계를 아예 보지 않았다. `importReview`가 사업동향에 다른 단계를 허용하지 않아 실제로 그런 행이 온 적은 없지만, 통과시키면 발행 단계가 조용히 떨어뜨리는 쪽이 된다. JS 검증에도 같은 검사를 넣었다.

### 정책 다이제스트

`config/approval_policy.json`을 `reviewPolicy()`와 `local_report`의 정책 해시에 넣었다. 어느 후보가 승인되는지가 바뀌면 모델이 문안을 써야 하는 후보도 바뀌기 때문이다. 지표 3·5의 품목 연결을 풀었을 때 저장된 판정에는 그 후보의 문안이 없었다. 상수만 고치고 기준 문서를 그대로 두면 옛 판정이 문안 없이 승인으로 올라온다.

## 4. GitHub 환경변수 — `app/lib/github_env.mjs`

`trigger-crawl`만 값을 다듬고(`trim` + 따옴표 제거) `crawl-status`와 `signals`는 원값을 썼다. Vercel 환경변수에 따옴표나 줄바꿈이 섞이면 실행 버튼은 동작하지만 상태 표시는 "확인 실패"가 되고 신호 조회는 말없이 로컬 파일로 떨어진다. 화면에는 크롤링이 돌아간 흔적이 없는 것처럼 보인다.

읽는 방법과 헤더 구성을 공용 모듈로 모으고 세 라우트가 그것만 쓰게 했다. 공백만 든 값은 없는 값으로 다룬다(예전에는 `owner`가 `" "`여도 설정된 것으로 세어 GitHub를 호출했다). 테스트는 동작과 함께, 라우트가 `process.env.GITHUB_*`를 직접 읽거나 헤더를 따로 만들지 않는지도 본다.

## 5. README 정정

- Python 수집기를 "Python equivalent"라고 적어 두었으나 동등하지 않다. `official_feeds`와 Google News만 읽고, Node 수집기의 공식 페이지·SEC·사이트맵·본문 수집·게시일 등급(`published_at_source`)·트렌드 탐색이 전부 없다(447줄 대 2,631줄). 그 행은 검토 단계가 요구하는 본문·날짜 근거를 갖추지 못한다. 설명을 사실대로 고쳤다.
- CSV 관련 서술을 현재 상태에 맞게 고쳤다.
- 새로 생긴 두 공용 파일을 파일 목록에 넣었다.

## 6. 구형 도구 표시

Python 수집기와 행 단위 요약기는 지우지 않고 월간 경로에서 쓰지 않는다고 README 와 파일 머리에 적었다. 진단과 비교 용도가 남아 있고 전용 테스트도 있다. `outputs/ai_summary_cache.json`(2.7MB)만 추적에서 내렸다. 그 캐시는 행 단위 요약기만 읽는다.

## 7. 보고서 출력 고정과 PDF 생성기 분리

### 먼저 출력을 고정했다

`tests/test_report_snapshot.py`가 고정 픽스처로 한·영 PDF 를 실제로 그리고 두 가지를 남긴다.

- 내용 계층의 판단(매트릭스 칸, 기업 상태, 시그널 카드 문안·출처·날짜, 사업현황 상자, 품목동향 카드) — `expected_content.json`
- 그려진 PDF 의 페이지별 텍스트 — `expected_pages_ko.txt`, `expected_pages_en.txt`

규칙이 옳은지 묻지 않는다. 오늘 나오는 결과와 같은지만 묻는다. 픽스처에는 이번에 새로 승인 가능해진 기업 단위 S3(품목 미연계) 행을 넣어, 지표 3·5 변경으로 열린 경로도 그려지게 했다. 기대값만 다시 찍어 차이를 없애는 일을 막으려고, 덮여야 할 경우가 픽스처에 남아 있는지 보는 검사도 함께 둔다.

    python tests/test_report_snapshot.py --update

### 그다음에 나눴다

`build_pdf_report.py` 2,302줄을 두 파일로 나눴다.

| 파일 | 줄 수 | 하는 일 |
|---|---|---|
| `scripts/report_content.py` | 1,237 | 무엇이 실리는가 — 승인, 날짜 읽기, 선정, 문안 가공. reportlab 없이 불러올 수 있다 |
| `scripts/build_pdf_report.py` | 1,139 | 어디에 그리는가 — 색·글꼴·좌표·여백·줄바꿈·표·카드·쪽 나눔 |

`build_pdf_report` 가 내용 계층을 그대로 다시 내보내므로 `build_pdf_report.<이름>` 은 예전과 같이 쓸 수 있다. `report_view_model.py`(화면·HTML 경로)와 테스트가 그 이름들로 들어오기 때문에 호출하는 쪽은 한 줄도 고치지 않았다.

언어(`LANG`)는 `set_language` 가 바꾸는 모듈 상태다. 여느 이름처럼 가져다 두면 사본이 생겨 언어를 바꾼 뒤에도 옛 값이 남는다. 읽기와 쓰기를 모두 내용 계층으로 넘기는 모듈 속성을 둬서, `report_view_model` 의 `report.LANG` 읽기도 `tests/test_pdf_layout.py` 의 `pdf.LANG = "en"` 대입도 예전처럼 동작한다.

### 나누는 동안 고정 테스트가 잡은 것

첫 분리에서 쪽 나눔 계산(`item_breaks` 일가)을 내용 계층으로 보냈는데, 그 함수들은 `ITEM_SECTION_FIRST_TOP` 같은 페이지 기하 상수를 읽는다. 스냅샷 테스트와 기존 레이아웃 테스트가 `NameError` 로 바로 드러냈다. 쪽 나눔과 여백 상수는 배치 계층에 남겼다. 이후 분리 스크립트에 "내용 계층이 배치 이름을 읽고 있으면 중단" 하는 정적 검사를 넣어, 실행해 봐야 알던 것을 미리 잡게 했다.

### 확인

- 스냅샷: 한·영 PDF 페이지 텍스트가 분리 전후 동일
- 실제 운영 자료(77개사·10쪽) PDF 추출 텍스트 8,979자, 분리 전후 해시 동일
- 화면 경로: `report_view_model.py` 출력 JSON 이 한·영 모두 바이트 단위로 동일
- Node 337개, Python 52개 테스트 통과, `next build` 성공

계층 경계를 지키는 검사도 넣었다(`tests/test_report_scope.py`): 내용 계층은 reportlab 을 불러오지 않고 페이지 좌표 상수를 쓰지 않으며, 배치 계층은 호출자가 쓰던 이름에 여전히 답한다.
