# NVIDIA 기사 분석 병렬 실행

Actions 실행 입력 `concurrency` 기본값은 3이며 1~8로 조절할 수 있다.
로컬에서는 `REPORT_CONCURRENCY`를 사용한다. 1은 기존 순차 처리다.

병렬 처리 수는 동시에 응답을 기다리는 기사 수다. 모든 작업자가 공유하는 요청 시작
제어기가 기본 1600ms 간격을 지키므로 3개를 한꺼번에 발사하지 않는다. 재시도도
동일한 간격과 실행당 요청 상한에 포함된다. 응답 대기는 다음 기사 요청을 막지 않는다.
40 RPM은 사용자 프로젝트의 관측 한도이며 이 설정이 서버 용량이나 토큰 한도를 보장하지는 않는다.

예를 들어 응답에 10초가 걸리면 기존 순차 처리는 기사당 약 11.6초가 필요하다.
3건 병렬은 응답 대기를 겹칠 수 있어 빨라진다. 실제 속도는 기사 길이·응답 시간·서버
상태에 따라 달라지므로 이 예시는 실측 결과가 아니다.

429가 확인되면 대기 중인 새 요청을 멈춘다. 이미 전송한 요청은 완료까지 기다리고,
검증된 결과를 저장한 뒤 일시정지한다. 인증 실패도 진행 중인 캐시 기록을 마친 뒤
오류를 반환한다. 개별 판정 오류는 기존 진단·재시도 규칙을 사용한다.
기존 모델·정책·기사 ID를 바꾸지 않으므로 저장된 NVIDIA 판정 캐시는 재사용한다.

검증: 병렬 응답 대기, 요청 시작 간격, 전역 요청 상한과 재시도, 429 시 신규 요청 중단,
인증 실패 시 진행 중 결과 저장, 재실행 캐시 재사용을 모의 응답 테스트로 확인했다.
실제 API 처리시간 개선은 수정본으로 Actions를 실행한 뒤 확인해야 한다.
